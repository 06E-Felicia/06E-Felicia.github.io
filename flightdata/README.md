# Flightdat 航班精选

主站页面为根目录 `Flightdat.html`，首页菜单已添加入口。由用户提供的 `爬FR24` 整合而来，支持深圳、北京首都、上海浦东、广州、香港、成都双流（CTU / ZUUU）、东京羽田（HND / RJTT）七机场，到达 / 出发、搜索、排序、当日历史、机型照片与署名，以及宽体 / 彩绘 / 外航 / 四发 / 货机筛选。新增机场的真实快照由后续采集任务生成，不补造数据；首次采集前显示“航班资料正在准备”。机场代码依据 [FR24 中国机场目录](https://www.flightradar24.com/data/airports/china)和 [FR24 羽田机场资料](https://www.flightradar24.com/data/airports/hnd)。

宽体展示同时修改前端筛选与采集器保留规则，宽体但没有彩绘、外航、货机等其他标记的航班不会再被过滤。“特殊机型”指四发或货机，不与宽体分类混淆；页面已移除公务机统计、筛选与标记，旧快照的相关字段仅为兼容保留。分类可交叉，但“精选航班”总数逐条去重计算，不累加各分类。

原文件夹与其中独立的 `.git` **没有删除或改写**，已在主项目中忽略，避免上传为嵌套仓库。本目录是主项目实际使用的采集器及快照；后续请修改这里的 `scraper.py` / `config.json`，而非原导入文件夹。照片请求的联系地址已指向本项目仓库。

## 数据与更新

- `docs/data/index.json`：机场索引，下一次采集后包含七机场。
- `docs/data/szx.json`、`pek.json`、`pvg.json`、`can.json`、`hkg.json`、`ctu.json`、`hnd.json`：页面读取的成功快照；后两项在新机场首次采集后生成。
- `docs/data/status.json`：最近一次采集的状态；同日失败时保留上次成功快照，跨日则先清空昨日列表，保留真实上次成功时间。
- `data/`：北京时间当天累计、彩绘注册号学习库、照片缓存。
- 根目录 `.github/workflows/flightdata.yml`：每 10 分钟尝试采集，由 `schedule.py` 按上次调度检查时间判断是否到期；未到期不安装浏览器、不抓取、不提交。管理员手动运行、跨日首轮或上次全部失败允许立即采集。采集与保存分开，只有最后的保存任务与天气任务共享提交锁。
- 航班工作流结束后，现有“自动更新天气数据”通过 `workflow_run` 读取主分支最新文件并发布全站。成功 / 失败状态都会发布，不新增独立 Pages 站点，也不把站点根目录改为 `/docs`。

已有快照可以直接显示，不需要先采集。页面“重新载入”只重新读取已发布的 JSON，不会替访客启动爬虫。时间统一按北京时间显示；定时任务可能延迟，源站也可能拒绝采集。数据是快照，不是实时航班保障信息，出行以机场 / 航司为准。

默认列表仅显示当前时刻至北京时间当日结束的精选航班，统计卡、分类计数和列表计数均不包含过去时刻或明日航班。优先按预计时间判断，没有有效预计时间时使用计划时间。顶部“显示之前时刻的航班”可展开当天已经抓到的历史记录，放在“现在”分界上方，保持当前阅读位置，向上滚动即可查看；展开不增加剩余计数。搜索和分类同时作用于历史与剩余航班，历史部分始终按时间正序排列。进入页面或切换机场后自动定位到“现在”，普通更新不强行跳转；跨日重新收起历史。

更新栏只显示最近成功更新时间；页面不展示抓取错误、部分更新原因或久未更新提示，失败不会伪造新时间或清空已载入航班。完整诊断仍保留于 `status.json` 和 Actions 日志。彩绘机使用高对比标签、侧边色条与可换行名称，过去航班不降低透明度，各行使用深色边界分隔。

点击航班或用 Enter / 空格打开大尺寸详情卡，展示航线、计划 / 预计时间、状态、航司、飞机注册号与机型、呼号、登机口、跑道、彩绘说明、照片来源及数据记录；没有数据的字段明确标为未提供。支持关闭按钮、Escape、点击背景、键盘焦点限制和关闭后焦点恢复，手机使用单列并在卡片内部滚动。列表与当天统计继续统一按北京时间；羽田卡片另外列出日本当地时间（UTC+9）。

历史文件带有 `service_day`。次日第一次采集开始前清空旧日累计，随后只积累新一天的记录；即使次日首次采集失败，也不把昨日数据当作今日数据保留。不删除历史文件本身，不伪造新成功时间，页面载入新快照时替换旧数组。照片缓存与彩绘知识库不是按日航班历史，不随航班换日清空。

原“已结束”只是计划或预计时间已过 25 分钟后的前端推断，并非源站确认，现改为同为三字的“待核实”；原“已到达”对应源站 `landed` / `arrived`，现改为“已落地”。页面页脚及状态悬停说明区分两者，未确认的航班不再误标成已经结束。

回归测试使用项目快照与离线故障样例；线上采集结果需要另行验收。

## 授权登录会话（24 小时查看范围）

Actions 不自动输入密码，也不读取普通 Chrome 的个人资料。需要账号已有相应查看权限，由本人在项目专用窗口登录：双击根目录 `development/launchers/配置FR24登录.command`，完成登录后按回车。程序重新访问机场看板，只有实际响应的 `hoursRange >= 24` 才保存会话；仅有 Cookie 不算验证通过。

导出文件在被 Git 忽略的 `flightdata/.auth/`，目录权限为 700、文件为 600。只保留 FR24 域的 Cookie / localStorage，排除其他网站和 Cloudflare 通行凭据。不要把该目录、文件内容或截图发到聊天、提交到仓库或作为附件上传。Base64 不是加密，文件相当于登录凭据，应妥善保管。

在本仓库 Settings → Secrets and variables → Actions 新建 Repository secret，名称严格为 `FR24_STORAGE_STATE_B64`，值为本机 `.auth/fr24-state.b64` 的完整内容。**只保存到 Secret，不是普通变量或代码文件。** 若本机已配置 GitHub CLI，可在项目根目录用 `gh secret set FR24_STORAGE_STATE_B64 --repo 06E-Felicia/06E-Felicia.github.io < flightdata/.auth/fr24-state.b64` 导入，命令不会包含令牌正文。

Secret 只传给采集步骤，在内存中还原到临时浏览器上下文；不写入 runner 文件、不传给测试和附件步骤。登录模式禁用诊断截图。每轮先验证源站的 24 小时权限，再按真实链接读取，每方向仍严格最多 10 页。Actions 摘要和 `status.json` 只记录 `session_requested` / `authenticated_24h` 及看板覆盖信息，不记录账号或凭据；24 小时权限并不代替全天分页完整性核验。

登录态可能过期、被撤销，或在 GitHub 网络中不可用。本地验证成功不保证 CI 可用；失效时保留同日成功数据、记录失败，不静默降为匿名或伪造全天覆盖。请本地重新登录并更新同名 Secret；停用时删除该 Secret，必要时在 FR24 注销该会话。不要关闭账号安全保护、自动处理验证码或绕过访问拒绝。

此方案使用 [Playwright 官方会话复用机制](https://playwright.dev/python/docs/auth)和 [GitHub Actions Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)，不是共享整个个人浏览器档案。

## 当日结束的分页判断

不再用“某页最大计划时间跨过午夜”判断覆盖完成：一条超远期航班或无序记录不能代表其余航班都已跨日。按源站真实的下一页链接持续读取，要求**连续两整页中的每条航班，其计划时间及有效预计时间都达到次日北京时间 00:00**，才记录 `boundary_confirmed=true`；混有当日记录或无效时间即重新开始确认。确认针对源站的整个看板，在精选筛选前完成，到达和出发分别判定。

每个机场每方向严格最多 **10 页**（包括首页），不假设每页固定覆盖 3 小时。末页旗标兼容布尔值、0 / 1、字符串及明确的双空游标；不把缺失整个分页结构当作正常结束。后台保存原始分页字段的安全摘要，便于核验序列化差异。

登录会话首次云端验收已确认七机场的 24 小时范围，深圳到达实际读取 6 页。官网部分末页仍返回 `hasMoreNextData=true`，但明确给出 `nextPage=null` 与正确的 `currentPage`；这属于末页，不再误报为缺少分页。仅在页码与实际已读页数一致且该页非空时接受这一组合，是否覆盖午夜仍独立按已知时间窗口判断；网络超时等真实错误不隐藏。

2026-10-20 08:31 的线上快照 `window_hours=12`，约覆盖 08:25–20:25；浏览器官网时间菜单最多可选到 20:00，之后的 Later time 禁用。此时增加页数不能取得尚未开放的 20:30–24:00。窗口耗尽记录为 `source_window_exhausted`，`available_complete=true` 但 `coverage_complete=false`，不是抓取故障，更不冒充全天已覆盖。随着官网可用窗口向后推进，后续更新自动补充新开放的航班；不猜测或绕过受限的日期参数。

源站明确没有后续页且无已知窗口限制时记录 `source_exhausted`；只有时间窗口本身达到午夜才可确认当日覆盖。达到安全上限、缺失分页信息、异常空页、分页循环或读取失败仍记录为部分更新，保留成功数据。`status.json` 按方向保存窗口起止、停止原因、原始航班数及跨日核验，Actions 摘要区分“窗口已读完”和“全天已覆盖”。

离线回归覆盖混入次日异常值、跨午夜的混合页、预计提前到当日、缺失时间、超过旧 6 页限制、下一页失败、重复页和安全上限；不会因此新增并发或绕过源站限制。

## 部分更新与源站访问失败

2026-10-19 的日志显示：深圳到达第一页取得 100 条航班，后续分页和出发看板显示 `Just a moment...` 访问验证。旧代码因出发看板失败丢弃整个机场已经取得的数据，并多次等待相同验证页面。此次失败并非 Node.js 版本警告，也不是保存任务缺少推送权限。

一般网络或解析错误仍按到达 / 出发独立处理；后续分页失败保留先前页，当日历史不伪装成新采集。HTTP 401 / 403 / 429 或明确访问验证会立即停止整轮后续看板和机场请求，不仅是停止当前页的重试。`status.json` 与 Actions 摘要保留“部分更新”、被停止的方向及真实原因，页面不显示技术诊断。部分采集也会令任务报错，保存任务仍先提交已取得的数据及状态；只有全部机场无采集错误才显示成功。有效的空航班列表不会因 JSON 太短被误判为拦截。

优先读取服务器 HTML 中的真实数据岛与分页链接，而不是依赖可能已经被官网脚本替换的 DOM。其他机场继续沿用已正常工作的原生 `Later flights` 导航，读取实际请求返回的 JSON 或 HTML。同页重复数据、错误机场、缺少航班字段都不会被当作翻页成功。

深圳到达也优先使用官网原生 `Later flights` 交互，兼容 Inertia JSON 和整页 HTML。该方向在页面内异步激活现有链接，由官网处理点击和 Inertia 请求，避免键盘聚焦长列表底部时卡住；其他机场仍使用 Enter。此前深圳固定另开标签页；2026-10-28 起第一张分页文档持续返回403，不能把这条路径当作必然可用。只有深圳交互超时且目标请求尚未发出时，才沿已观察到的官网链接在同一上下文读取备用文档；收到403、请求在途或已收到响应后均禁止重发。不会猜测额外 API、更换身份或复制验证通行凭据。

访问拒绝后的冷却记录写入公开状态，首次30分钟，连续失败依次1小时、2小时、4小时，之后最高6小时；源站 `Retry-After` 更长时遵守它（最多24小时）。跨日、手动运行和直接运行采集器均遵守冷却，跳过时不创建浏览器、不访问源站，也不重写采集时间。恢复后重置失败计数。普通全部失败也不再绕过正常十分钟间隔。

原本地启动器选择系统 Chrome，而此前整合的 CI 使用默认 Chromium headless shell。现 CI 明确安装并使用完整 Chrome，在 xvfb 窗口环境执行，不再伪装旧版 macOS Chrome/131 或修改浏览器特征。指定 Chrome 启动失败时报告实际错误，不在 CI 静默降级。此调整依据 [Playwright 浏览器说明](https://playwright.dev/python/docs/browsers)，分页响应处理依据 [Inertia 协议](https://inertiajs.com/the-protocol)。

真实 Chrome 离线回归还覆盖其他机场“第一页 HTML → 第二页 Inertia JSON → 第三页 HTML”的完整流程，同时故意让初始数据岛保持不变，确认不会误读第一页。可运行 `python development/tests/test_flightdata_pagination.py -v`。该文件已加入 CI 的采集前检查，上传修复时必须一并上传。

这些修复保证可用数据不会丢失、状态不会误报，**不会绕过 Cloudflare，也不保证 GitHub 托管网络可以访问全部看板**。若源站持续拒绝访问，应采用获得授权的数据接口或符合其规则的采集环境。

## 更新周期的边界与解决方案

2026-10-19 检查时，工作流 API 状态为 active，但最近五轮均为手动触发；最近一轮总耗时 4 分 25 秒，并非长任务占满半小时。GitHub [官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) 明确指出 schedule 在高负载时可能延迟或被丢弃，原来的每半小时 cron 不能保证准点更新。

现采用十分钟唤醒、十分钟正常采集间隔，使用上次调度检查时间计时（旧状态回退到采集开始时间），避免浏览器安装与测试耗时误跳过下一轮；允许30秒调度抖动。无采集的检查不修改 freshness，也不重新发布整站。手动更新可跳过正常间隔，但不能跳过源站拒绝后的冷却。此方案**仍不能保证严格每十分钟触发或完成**，不为补偿延迟而并发访问源站。

若要求更可靠的准时触发，需要独立于 GitHub schedule 的定时器，例如现有常开电脑的系统定时任务或第三方定时服务，通过官方 `workflow_dispatch` 接口唤醒 GitHub；采集与网站仍可留在 GitHub。该方案涉及持续在线条件、第三方配置和 GitHub 授权，尚未创建或启用；即使外部触发，Actions runner 排队与源站可用性仍不能保证准点完成。不要把访问令牌放在网页或公开仓库中。

## 本地使用

在**项目根目录**启动现有预览：

```bash
python3 -m simulation.preview
```

将终端打印的网址路径改为 `/Flightdat.html`。不要用 `file://` 直接打开。

需要手动采集时，在项目根目录执行：

```bash
python3 -m pip install -r flightdata/requirements.txt
python3 -m playwright install chromium
python3 flightdata/scraper.py
```

采集器按自身所在目录读写，和终端当前目录无关。请遵守数据提供方的访问规则；失败时检查状态，不要将空数据伪装为新快照。上传时包括 `Flightdat.html`、整个 `flightdata/`、两份根目录工作流、首页入口及原有 `.nojekyll`，不需要上传 `爬FR24/`。
